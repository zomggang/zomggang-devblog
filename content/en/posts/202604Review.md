## What We Built

A study community + AI curation service. Main features:

- **Community**: Boards / Posts / Comments / Likes
- **AI Curation**: Daily RSS feed collection → Ollama (LLM) generates Korean/Japanese summaries
- **AI Bot Comments**: When a user posts, an AI bot automatically comments
- **Daily Digest**: Every day at 10 AM (KST), AI summarizes the day's curations into one digest and publishes it as a community post

Stack: Kotlin + Spring Boot 3.4.5 / PostgreSQL 16 + Flyway / RabbitMQ / Ollama (local LLM) / React + Vite + TypeScript / AWS + Cloudflare / CI-CD GitHub Actions

### Phase 2: AI Bot Comment Implementation (Early–Mid April)

- `OllamaClient` implementation (chat / generate API separation)
- AI bot auto-comment feature (BE-55): automatic AI bot comment when a post is saved
- Migration to `@TransactionalEventListener(AFTER_COMMIT)` + `@Async` + RabbitMQ async processing

**✅ What went well**: Properly applying the "publish event only after transaction commit" pattern guaranteed that "if post save fails, no comment is published."

**❌ The ordeal — Ollama 502 half-day debugging incident**

I replaced `OllamaClient` three times in total. The process was a small disaster.

First I chose JDK HttpClient to follow Spring standards. Locally, Ollama API calls worked fine. But after production deployment, 502 errors suddenly flooded in.

```
[Diagnosis process]
Call Ollama with curl → ✅ Normal
Call Ollama with Java → ❌ 502
```

curl worked but Java didn't. I thought it was a code problem and added retry logic, diagnostic logs, and timeout settings. I struggled all day but still got 502. I finally found the cause at 1 AM.

**Root cause: JA3 Fingerprint**

When HTTPS communication begins, there's a "TLS handshake" between the client (Java app) and server (Cloudflare). A hash value made from the TLS version, supported cipher suites, extension list, etc. is a **JA3 fingerprint**. Like a human fingerprint, each HTTP client generates its own unique JA3 value.

```
curl              → JA3: aaa... (passes)
Chrome browser    → JA3: bbb... (passes)
JDK HttpClient    → JA3: ccc... (Cloudflare classifies as Bot → 502 blocked)
Apache HttpClient → JA3: ddd... (passes)
```

Cloudflare's Bot Fight Mode blocks known bot JA3 values. JDK HttpClient generates a JA3 pattern distinct from browsers or curl, so it was classified as a bot. It wasn't a code problem — it was the TLS handshake pattern.

```kotlin
// Before (JDK, Cloudflare blocks)
JdkClientHttpRequestFactory()

// After (Apache, passes)
HttpComponentsClientHttpRequestFactory()
```

The problem didn't end there. I fixed the client for AI bot comments, but the Ollama client in the RSS curation pipeline had the same issue. If I had made `OllamaConfig` a shared bean from the start, one fix would have been enough.

### Phase 3: RSS Collection + Ollama Curation Pipeline (Mid April, BE-37)

This was the biggest feature.

1. `RssFeedClient` — RSS/Atom parsing, UTC normalization
2. `CollectedFeedItem` — url_hash/title_hash deduplication
3. `FeedItemPublisher` — RabbitMQ publishing (with DLQ)
4. `FeedCollectionScheduler` — automatic collection every day at 07:00 KST
5. `CurationService` — Ollama generate → simultaneous Korean/Japanese summary generation → save to curations
6. `AdminFeedController` — manual trigger API

**✅ What went well**:
- Including RabbitMQ DLQ in the design from the start secured a reprocessing path for failed items.
- Designing curation summaries to generate Korean/Japanese simultaneously (1 API call) was efficient.

**❌ The ordeal — 4 Consecutive Hotfix Incident**

After finishing RSS pipeline implementation and deploying, 3 bugs hit simultaneously. I ended up submitting 4 consecutive hotfix PRs within 4 days.

```
PR #142 (4/14)  hotfix: application-prod.properties restore and CI/CD DB credential injection
PR #146 (4/16)  hotfix: Ollama 502 — add retry logic (cause still unknown)
PR #147 (4/17)  hotfix: JDK HttpClient → Apache HttpClient (JA3 blocking was the real cause)
PR #148 (4/17)  hotfix: Apply same replacement to RSS curation pipeline
PR #151 (4/18)  fix:    Change PROD RabbitMQ host to host.docker.internal
```

Common thread across all three bugs: **None of them reproduced locally.** The production environment (Cloudflare, Docker networking, CI/CD environment variables) differed from local. But I verified "it works" locally and deployed immediately. If I had a production environment prerequisite checklist, at least bugs 1 and 4 could have been prevented.

## Vibe Coding + AI Usage Retrospective

### What Worked Well

**1. Context management with CLAUDE.md + wiki**

Specifying stack, API response format, Flyway rules, and auth patterns in `CLAUDE.md` was the biggest asset. Claude Code automatically followed existing patterns when implementing new features. Conversely, design decisions not documented anywhere repeatedly led Claude Code to implement in the wrong direction.

> **Lesson**: Before telling AI to "write code," record "why we designed it this way" first.

**2. Branch/worktree isolation**

Isolating by feature with worktrees and telling Claude Code to "only work in this branch" was good.

**3. Using sub-agents**

The implement → spec reviewer → code quality reviewer → next implement pattern was effective not for "quality of output" but for "finding what I missed."

---

### What Didn't Work / Lessons Learned

**1. "Just write it" without design**

Replacing the Ollama client three times, adding the type column to curations later — all are results of "let's just make something first."

The faster AI generates code, the **stronger the temptation to skip design**. This is the biggest trap of vibe coding.

**2. One revert ruined 2 months of context management**

```
2026-04-09  417b847  create claude skills and settings
2026-04-11  288f05f  Revert "create claude skills and settings"  ← reverted 2 days later
```

I built session management automation on April 9th, then reverted it 2 days later. As a result, for the following 2 months, Claude Code kept asking about already-decided matters or implementing in the wrong direction every new session.

Conclusion: **If you make a tool, use it.** Don't revert.

**3. Code I didn't understand**

I merged quickly generated code without understanding it sufficiently. "Why is this code like this?" kept repeating later.

> **Lesson**: Even for code AI wrote, I need to be able to explain it verbally. If I can't, stop first and understand.

**4. Prompt quality = Code quality**

Vague requests ("fix this") produced vague results. The more specific — "current situation → desired result → constraints" — the better the results.

## Structural Regrets

| Issue | Cause |
|-------|-------|
| `notifications` schema-only, incomplete | Priority kept getting pushed, nobody owned it |
| `last_login_at`, `user_activities` missing | Didn't discuss need for analytics metrics at the start |
| No soft delete | "We can add it later" → Never did |
| Missing FK indexes | Didn't know because we never did performance testing |
| No `isLiked` field | BE didn't realize FE needed it until FE said so |
| UUID vs BIGSERIAL mixed | No clear ID strategy discussion, decided case by case |

> **Common cause**: Skipping design discussions under the name of "focusing on MVP."

---

## Next Time, I'll Do This

1. **Do DB design review in Sprint 0.**
2. **Write design documents (wiki) before code.**
3. **Don't merge AI-written code until I can explain it myself.**
4. **Put analytics metric columns into the design on Day 1.**
5. **Write prompts properly.** Use "current situation → desired result → constraints" instead of "fix this."

---

## Closing

Over 2 months, I got to feel what "working with AI" is really like. AI was definitely fast. I built features that I couldn't have built within 2 months working alone.

But AI runs fast in the wrong direction if I point it the wrong way. The speed of vibe coding also increases the speed of mistakes.

In the end, what engineers need in the AI era isn't "the ability to write code well" but **"the ability to clearly know what and why we're building."**
