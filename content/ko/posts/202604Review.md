> 2026년 3월 ~ 4월, 도쿄 기반 한국인/일본인 스터디 커뮤니티 + AI 큐레이션 서비스를 팀 프로젝트로 만들었다.
> 나는 백엔드 엔지니어 리드를 맡았다. AI(Claude Code)와 함께 "바이브코딩"을 해봤고, 이 글은 그 반성문이다.

---

## 무엇을 만들었나

스터디 커뮤니티 + AI 큐레이션 서비스다. 주요 기능:

- **커뮤니티**: 게시판 / 글 / 댓글 / 좋아요
- **AI 큐레이션**: 매일 RSS 피드를 수집 → Ollama(LLM)로 한국어/일본어 요약 생성
- **AI 봇 댓글**: 사용자가 글을 올리면 AI 봇이 자동으로 댓글
- **Daily Digest**: 매일 10시(KST) 하루치 큐레이션을 AI가 하나의 다이제스트로 정리, 커뮤니티에 포스트로 게시

스택: Kotlin + Spring Boot 3.4.5 / PostgreSQL 16 + Flyway / RabbitMQ / Ollama(로컬 LLM) / React + Vite + TypeScript / AWS + Cloudflare / CI-CD GitHub Actions

---

## 타임라인 — 내가 한 것들

### Phase 1: 프로젝트 셋업 (3월 말)

- BE 프로젝트 초기화 (Kotlin + Spring Boot 3.4.5, Gradle, JPA, Swagger, Flyway, Logback)
- Google OAuth + JWT 인증 구현
- DB 스키마 초기 설계 (V1~V16, Flyway 마이그레이션 전략 수립)
- CORS, 리버스 프록시(Cloudflare) 뒤에서 HTTPS 스킴 인식 수정

**✅ 잘 된 것**: 처음부터 Flyway + "기존 파일 수정 금지" 규칙을 잡아놓은 덕에 팀 전체가 마이그레이션 충돌 없이 DB를 관리할 수 있었다.

**❌ 놓친 것**: 이 시점에 DB 설계를 더 꼼꼼히 했어야 했다. 나중에 보니 `notifications` 테이블은 스키마만 있고 엔티티가 없고, `last_login_at`, `user_activities` 같은 분석용 컬럼은 애초에 빠져 있었다.

### Phase 2: AI 봇 댓글 구현 (4월 초~중순)

- `OllamaClient` 구현 (chat / generate API 분리)
- AI 봇 자동 댓글 기능 (BE-55): 포스트 저장 시 AI 봇 댓글 자동 생성
- `@TransactionalEventListener(AFTER_COMMIT)` + `@Async` + RabbitMQ 비동기 전환

**✅ 잘 된 것**: 트랜잭션 커밋 후 이벤트 발행이라는 패턴을 제대로 적용해서 "포스트 저장 실패 시 댓글 발행 안 됨" 보장을 얻었다.

**❌ 삽질한 것 — Ollama 502 반나절 디버깅 사건**

`OllamaClient`를 총 세 번 교체했다. 그 과정이 하나의 작은 재난이었다.

처음엔 Spring 표준에 맞춰 JDK HttpClient를 선택했다. 로컬에서는 Ollama API 호출이 잘 됐다. 그런데 프로덕션 배포 후 갑자기 502 에러가 쏟아졌다.

```
[진단 과정]
curl로 Ollama 호출 → ✅ 정상
Java로 Ollama 호출  → ❌ 502
```

curl은 되는데 Java만 안 됐다. 코드 문제라고 생각하고 retry 로직, 진단 로그, timeout 설정을 추가했다. 하루 종일 삽질했지만 여전히 502였다. 그러다 새벽 1시에야 원인을 찾았다.

**원인: JA3 핑거프린트 — 간단한 설명**

HTTPS 통신을 시작할 때, 클라이언트(Java 앱)와 서버(Cloudflare) 사이에 "TLS 핸드셰이크"라는 과정이 있다. 이 과정에서 클라이언트는 서버에게 이런 메시지를 보낸다:

> "나는 TLS 1.3을 쓸 수 있고, 이런 암호화 방식들을 지원하고, 이런 확장 기능들을 쓸게."

이 메시지에 담긴 값들을 하나의 해시값으로 만든 것이 **JA3 핑거프린트**다. 사람의 지문처럼, HTTP 클라이언트마다 고유한 JA3 값이 나온다.

```
curl              → JA3: aaa... (통과)
Chrome 브라우저    → JA3: bbb... (통과)
JDK HttpClient    → JA3: ccc... (Cloudflare Bot으로 분류 → 502 차단)
Apache HttpClient → JA3: ddd... (통과)
```

Cloudflare의 Bot Fight Mode는 알려진 봇의 JA3 값을 차단한다. JDK HttpClient는 일반적인 브라우저나 curl과 다른 독특한 패턴의 JA3를 생성해서 봇으로 분류됐다.

```kotlin
// Before (JDK, Cloudflare 차단)
JdkClientHttpRequestFactory()

// After (Apache, 통과)
HttpComponentsClientHttpRequestFactory()
```

문제는 이게 끝이 아니었다. AI 봇 댓글용 클라이언트는 고쳤는데, RSS 큐레이션 파이프라인의 Ollama 클라이언트는 따로 또 같은 문제가 터졌다. 처음부터 `OllamaConfig`를 공유 빈(Bean)으로 만들었다면 한 곳만 고쳐도 됐을 것이다.

### Phase 3: RSS 수집 + Ollama 큐레이션 파이프라인 (4월 중순, BE-37)

가장 큰 기능이었다.

1. `RssFeedClient` — RSS/Atom 파싱, UTC 정규화
2. `CollectedFeedItem` — url_hash/title_hash 중복 제거
3. `FeedItemPublisher` — RabbitMQ 발행 (DLQ 포함)
4. `FeedCollectionScheduler` — 매일 07:00 KST 자동 수집
5. `CurationService` — Ollama generate → 한/일 요약 동시 생성 → curations 저장
6. `AdminFeedController` — 수동 트리거 API

**✅ 잘 된 것**:
- RabbitMQ DLQ를 처음부터 설계에 넣어서 실패 아이템 재처리 경로를 확보했다.
- 큐레이션 요약을 한/일 동시 생성(API 1회 호출)으로 설계해서 효율적이었다.

**❌ 삽질한 것 — Hotfix 4연속 사건**

RSS 파이프라인 구현을 마치고 배포했더니, 버그가 3가지가 동시에 터졌다. 결국 4일 안에 hotfix PR을 4개 연속으로 냈다.

```
PR #142 (4/14)  hotfix: application-prod.properties 복원 및 CI/CD DB 크레덴셜 주입
PR #146 (4/16)  hotfix: Ollama 502 — retry 로직 추가 (원인 아직 모름)
PR #147 (4/17)  hotfix: JDK HttpClient → Apache HttpClient (JA3 차단이 진짜 원인)
PR #148 (4/17)  hotfix: RSS 큐레이션 파이프라인에도 동일 교체 적용
PR #151 (4/18)  fix:    PROD RabbitMQ 호스트를 host.docker.internal로 수정
```

세 버그의 공통점: **모두 로컬에선 재현이 안 된다.** 프로덕션 환경(Cloudflare, Docker 네트워크, CI/CD 환경변수)이 로컬과 달랐다. 근데 로컬에서 "됩니다" 확인하고 바로 배포했다. 프로덕션 환경 전제조건을 체크리스트로 만들어놨더라면 적어도 1번과 4번은 막을 수 있었다.

## 바이브코딩 + AI 활용 회고

### 잘 사용한 방식

**1. CLAUDE.md + wiki로 컨텍스트 관리**

`CLAUDE.md`에 스택, API 응답 포맷, Flyway 규칙, 인증 패턴을 명시해둔 것이 가장 큰 자산이었다. Claude Code가 새 기능을 짤 때 기존 패턴을 자동으로 따랐다. 반대로 wiki나 CLAUDE.md에 없는 설계는 Claude Code가 잘못된 방향으로 짜는 일이 반복됐다.

> **교훈**: AI에게 "코드를 짜라"기 전에 "왜 이렇게 설계했는지"를 기록하는 게 먼저다.

**2. 브랜치/worktree 격리**

worktree로 기능별 격리 후 Claude Code에 "이 branch에서만 작업해라"고 지정한 건 좋았다.

**3. 서브에이전트 활용**

구현 → 스펙 리뷰어 → 코드품질 리뷰어 → 다음 구현 패턴은 "결과물의 품질"보다는 "내가 놓친 부분 발견"에 효과적이었다.

---

### 잘못 사용한 방식 / 반성

**1. 설계 없이 "일단 짜봐"**

Ollama 클라이언트를 세 번 교체한 것, curations 테이블 type 컬럼을 나중에 추가한 것, 모두 "일단 만들고 보자"의 결과다.

AI가 빠르게 코드를 생성해주는 만큼, **설계를 건너뛰는 유혹이 더 강해진다**. 바이브코딩의 가장 큰 함정이 여기에 있다.

**2. Revert 하나가 2달의 컨텍스트 관리를 망쳤다**

```
2026-04-09  417b847  create claude skills and settings
2026-04-11  288f05f  Revert "create claude skills and settings"  ← 이틀 뒤 되돌림
```

4월 9일에 세션 관리 자동화를 만들었다가 이틀 뒤 Revert했다. 그 결과 이후 2달 내내 세션이 새로 시작될 때마다 이미 결정된 사항을 Claude Code가 모르고 다시 물어보거나 잘못된 방향으로 짰다.

결론: **도구를 만들었으면 써라.** Revert하지 말고.

**3. 내가 이해 못 한 코드**

빠르게 생성된 코드를 충분히 이해하지 않고 머지했다. 나중에 "이 코드 왜 이렇게 돼 있지?"라는 상황이 반복됐다.

> **교훈**: AI가 짠 코드라도 내가 말로 설명할 수 있어야 한다.

**4. 프롬프트 품질 = 코드 품질**

모호한 요청("이거 좀 고쳐봐")은 모호한 결과를 냈다. 구체적으로 "현재 상황 → 원하는 결과 → 제약 조건" 형식으로 쓸수록 결과가 좋았다.

## 구조적으로 아쉬운 것들

| 이슈 | 원인 |
|------|------|
| `notifications` 스키마만 있고 미완성 | 우선순위 밀림, 아무도 챙기지 않음 |
| `last_login_at`, `user_activities` 없음 | 분석 지표 필요성을 처음에 논의 안 함 |
| soft delete 없음 | "나중에 추가하면 됨" → 안 함 |
| FK 인덱스 누락 | 성능 테스트를 안 해서 몰랐음 |
| `isLiked` 필드 없음 | FE가 필요하다고 말하기 전까지 BE에서 인지 못함 |
| UUID vs BIGSERIAL 혼용 | 명확한 ID 전략 논의 없이 그때그때 결정 |

> **공통 원인**: "MVP에 집중"이라는 이름 아래 설계 논의를 건너뛴 것.

## 다음엔 이렇게 하겠다

## 마치며

2달 동안 "AI와 함께 일하는 것"이 어떤 것인지 체감했다. AI는 분명히 빨랐다. 혼자 짰다면 두 달 안에 못 만들었을 기능들을 만들었다.

하지만 AI는 내가 잘못된 방향을 가리키면 그 방향으로 빠르게 달려간다. 바이브코딩의 속도는 실수의 속도도 높인다.

결국 AI 시대의 엔지니어에게 필요한 건 "코드를 잘 짜는 능력"이 아니라 **"무엇을 왜 만드는지 명확하게 아는 능력"** 이라는 걸 배웠다.
